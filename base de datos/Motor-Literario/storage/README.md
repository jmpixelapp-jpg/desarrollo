# MLDB Storage — etapa experimental

Este crate contiene componentes iniciales del almacenamiento propio. **No es una base de datos lista para manuscritos.**

## Restricciones

- Rust 2021 y biblioteca estándar únicamente: cero dependencias externas.
- Toda clave de datos narrativos exige `project_id`, tabla e identificador.
- La clave lógica del WAL de registros es `(project_id, table, record_id)`.
- El WAL de registros confirma una transacción con BEGIN, operaciones y COMMIT; publica cambios en memoria solo después de sincronizar el WAL. La recuperación descarta solo colas parciales al final y rechaza frames completos corruptos, mal formados o con IDs no crecientes (se permiten huecos históricos para compatibilidad). Si una escritura o sincronización falla después de tocar el archivo, bloquea lecturas/escrituras de esa instancia y exige reabrir: no trunca ni reutiliza un ID de transacción cuyo resultado pueda ser ambiguo.
- FNV-1a detecta daños accidentales; no es firma, autenticación ni protección criptográfica.

## Publicación conjunta de los almacenes vivo y narrativo

El protocolo objetivo para publicar ambos almacenes como una sola generación está definido en [BUNDLE_PUBLICATION_PROTOCOL.md](BUNDLE_PUBLICATION_PROTOCOL.md). El módulo `src/bundle.rs` incorpora codecs versionados, `BundlePublicationStore` con un único selector `CURRENT.0/CURRENT.1`, verificación de ambos miembros, `PublishedBundle` read-only, `WorkingBundle` persistente con lock de sesión compartido y validador clonable; el worker del motor revalida la identidad del lock antes de abrir documentos, confirmar deltas, resincronizar, checkpointar o cerrar documentos, y la API valida antes de mutar registros narrativos y al rebasar evidencias. Además, `ProjectStore` conserva el mismo `SessionLockValidator` y lo comprueba dentro de `put_project`, `delete_project`, `apply_batch`, `repair_occupancy` y `checkpoint`; `ProjectStore::open_existing_with_session_validator` comprueba el lock tras abrir los descriptores y antes de recovery; `NarrativeKnowledgeStore::open_existing_with_session_validator` usa esa apertura y conserva el validador para cada mutación, por lo que las escrituras directas también fallan cerradas fuera de `HostEngineApi`. `PersistentLiveEngine::open_existing_with_session_validator` utiliza el mismo constructor protegido para el almacén vivo; por tanto, sus transacciones `apply_batch` quedan ligadas al lock incluso cuando el motor se usa directamente sin pasar por `LiveEngineWorker`. La apertura valida el lock antes y después de abrir ambos almacenes. La suite incluye una prueba específica de Windows que sustituye el lock de sesión después de sincronizar el selector temporal y comprueba que no se crea el enlace de activación ni cambia la generación vigente; las pruebas de recovery por interrupción entre imágenes y reapertura también son multiplataforma. En Windows, la identidad de MLPG, MLPJ y los miembros de bundle se compara mediante número de volumen e índice de archivo, no por tamaño; se rechazan hardlinks mediante el contador de enlaces y hay pruebas específicas para archivos distintos de igual longitud y archivos compartidos. La recuperación también tiene pruebas de reapertura tras una interrupción entre imágenes de redo y tras aplicar commits antes de truncar una cola parcial. El coordinador `DurablePages` conserva el validador dentro de la capa WAL: lo comprueba antes de reparar la cabecera, entre la validación y el redo de cada imagen de página, antes de truncar una cola incompleta y antes de sincronizar páginas recuperadas. En `checkpoint`, vuelve a validarlo después de sincronizar las páginas y justo antes de truncar el WAL; si la sesión fue sustituida, el diario permanece intacto. Si la ruta del lock se sustituye, las siguientes mutaciones fallan cerradas; esto reduce la ventana de sustitución, sin eliminar la carrera residual de un proceso hostil con el mismo usuario entre validación y escritura. También se comprueba el validador compartido en la prueba de sustitución del lock. La implementación mantiene la validación de identidad/permisos de archivos y rechazo de symlinks y hardlinks en sus miembros, además de creación/reapertura de copias independientes. `publish_working_bundle()` checkpointa ambos almacenes, valida aislamiento por `project_id`, prepara ambos receipts/manifiesto y conmuta un único selector. El motor anfitrión ya puede abrir una working bundle mediante `HostEngineApi::open_working_bundle()` y devolverla cerrando el worker con `into_working_bundle()`. Se añadieron failpoints privados para diez fronteras de preparación: ambos checkpoints, las cuatro copias de archivos, ambos receipts, el manifiesto común y la sincronización de directorios. Cada interrupción se comprueba reabriendo y verificando que el selector conserva el bundle anterior completo. Sigue pendiente ejecutar la suite real. No promover los dos almacenes por separado como una misma revisión.

## Componentes

### WAL de registros

Archivo de operaciones append-only v1. Permite transacciones de varias operaciones y recuperación de commits completos. `Store::visit_records` recorre el snapshot recuperado en orden determinista, presta los bytes sin clonar el mapa completo y mantiene el bloqueo mientras se ejecuta el visitante; rechaza instancias con resultado de escritura ambiguo. Esta API es una base para el migrador, no una migración completa. No integra aún la validación del esquema MLDB 0.2 ni compactación. La apertura usa un guard de bloqueo exclusivo del kernel. Durante la publicación conjunta, los stores de trabajo se abren con verificación sobre los descriptores ya abiertos, bajo los locks de páginas/WAL y antes de ejecutar recovery, redo o truncado. La copia a la generación nueva también lee desde un descriptor verificado, rechaza symlinks/hardlinks, exige permisos privados y vuelve a comprobar identidad, tamaño y metadatos al terminar. El hash de la copia se calcula sobre el descriptor de destino que recibió los bytes, sin reabrir la ruta. Al verificar generaciones publicadas, los hashes de pages/WAL se contrastan con los receipts sobre los mismos descriptores bloqueados que usa DurablePages, antes de recovery; se rechazan sustituciones de ruta, symlinks y hardlinks. La lectura de selectores, manifiestos y receipts también exige archivos privados sin hardlinks y vuelve a comprobar el descriptor y la ruta al terminar la lectura. La validación de bundles recorre además cada directorio desde la raíz hasta `generations/<generation>/{live,knowledge}` y rechaza cualquier ancestro sustituido por symlink, tanto al verificar como antes de abrir los miembros read-only. `open_current_bundle()` vuelve a comprobar ambas cadenas inmediatamente antes de abrir cada miembro y después de abrir los dos descriptores; las pruebas de sustitución de `generations/` y `live/` cubren también la apertura read-only, no solo `verify_current()`. En Linux/Android, los auxiliares de bloqueo se abren con `O_NOFOLLOW`; después se verifica la identidad del descriptor, que sean archivos regulares, privados y sin hardlinks. En Windows también se compara el volumen y el índice de archivo del descriptor con los de la ruta, y se exige un único enlace; hay una prueba específica de sustitución del lockfile durante una sesión. Las operaciones MLPJ de escritura y checkpoint vuelven a validar que cada ruta de lock siga apuntando al descriptor bloqueado; si un lockfile se sustituye durante la sesión, la siguiente mutación falla cerrada antes de tocar el WAL. También se comprueba la identidad de las rutas MLPG y MLPJ frente a sus descriptores abiertos antes de leer/escribir páginas, antes de añadir frames y antes de truncar el diario; una sustitución detectada impide iniciar el commit y conserva intactos los archivos originales. Estas comprobaciones reducen las ventanas de sustitución, pero no equivalen a una protección absoluta frente a un proceso hostil con el mismo usuario que pueda competir entre la última validación y la operación del sistema de archivos. En Unix, los archivos MLPG, MLPJ y los auxiliares de bloqueo nuevos se crean con modo máximo `0600` (solo el usuario propietario, sujeto a un `umask` que puede restringirlo aún más); los permisos de archivos preexistentes no se modifican. En Windows se heredan las ACL del directorio y no se promete una política equivalente explícita.

### Archivo de páginas MLPG v1

Páginas fijas de 4096 bytes, con cabecera, ID, generación, longitud y checksum. Incluye lectura, asignación, reemplazo y apertura para recuperación. No es por sí solo un gestor de páginas completo.

### Páginas slotted MLSP v1

Codec de registros variables dentro del payload de una página. Conserva posiciones de slots y usa tombstones. No implementa asignación/reutilización de slots ni gestión de páginas.

### Nodos B+Tree MBTN v1

Codec de nodos hoja e internos, con claves ordenadas y enlaces entre hojas. La administración persistente (búsqueda, inserción, splits, rangos y validación) está en `src/btree.rs`; el codec por sí solo no hace I/O ni administra el árbol.


### Unificación del WAL legado y ProjectStore

El análisis de la transición entre MLWAL v1 (`Store`) y el backend nuevo (`ProjectStore` + MLPG/MLPJ) está en [STORE_UNIFICATION_PLAN.md](STORE_UNIFICATION_PLAN.md). Ambos sistemas siguen separados: no existe coordinación transaccional ni se permite escritura dual del mismo conjunto de datos. El documento define la arquitectura objetivo recomendada, la extracción del origen, la importación aislada, la verificación registro por registro, la publicación reversible y las pruebas necesarias. No se ha activado ninguna migración ni se ha modificado el formato de los datos existentes.

### Fachada ProjectStore sobre B+Tree

Se añadió `src/project_store.rs`, exportado como `project_store`. `ProjectStore` conecta registros del dominio con `PersistentBPlusTree` y exige que el programa anfitrión entregue `project_id`, tabla e identificador en cada operación. Ofrece `put_project`, `get_project`, `delete_project`, `apply_batch` con `ProjectOperation`/`ProjectBatchResult`, recorrido materializado `scan_project_table` y recorrido incremental `scan_project_table_iter` y recorrido global `scan_all_iter`, ambos sin materializar todo el conjunto.

La clave compuesta codifica por separado los tres componentes con una versión de formato explícita, escape de bytes NUL y terminadores, evitando colisiones entre proyectos/tablas/IDs y permitiendo intervalos de rango acotados. La validación del tamaño incluye también el byte de versión y comprueba que el prefijo de cada recorrido deja espacio para un ID no vacío. El iterador incremental limita la consulta al proyecto y tabla exactos y no materializa toda la tabla. La fachada no genera ni asigna identidades de proyecto: recibe las del anfitrión.

Las escrituras individuales se confirman como transacciones MLPJ. `apply_batch` prepara una secuencia ordenada de operaciones explícitas, valida todas las identidades antes del staging, observa los cambios anteriores del mismo lote y confirma una única transacción MLPJ; los resultados se devuelven solo después del commit. Los `Delete` informan si la clave existía inmediatamente antes de esa operación. Un lote compuesto solo por eliminaciones ausentes es un no-op sin COMMIT vacío. Si falla la escritura/sync del WAL o la aplicación de páginas después de un COMMIT durable, el error puede ser ambiguo: no se debe reintentar sobre la misma instancia; hay que cerrarla y reabrirla para completar recovery. No existe coordinación transaccional con el WAL legado de registros. El almacén anterior `Store` sigue existiendo como implementación separada; no debe confundirse con `ProjectStore`.

### B+Tree persistente experimental
El diseño, los hitos implementados y las tareas pendientes de la reparación descendente están en [DESCENDING_UNDERFLOW_REPAIR_PLAN.md](DESCENDING_UNDERFLOW_REPAIR_PLAN.md). Define el algoritmo acotado al camino afectado, la resolución de padres después de fusiones, el acumulador único de imágenes y las pruebas estructurales/de recuperación.


Se añadió `src/btree.rs`, exportado como `btree`. `PersistentBPlusTree` usa MLPG para nodos y MLPJ para confirmar cada inserción como una transacción atómica de páginas. La página 0 conserva metadata de raíz; las páginas siguientes contienen nodos MBTN. Implementa apertura/inicialización, búsqueda exacta, inserción/reemplazo, eliminación con redistribución/fusión local, pasada descendente acotada para reparar nodos internos unarios y hojas vacías cuando aparecen hermanos válidos, liberación MBFR y contracción de cadenas de raíces unarias, división de hojas e internos, enlaces entre hojas, consultas por rango semiabierto y actualización transaccional de raíz. Las claves se comparan como bytes lexicográficos; el llamador debe proporcionar una codificación estable de la clave compuesta del dominio. El árbol limita cada clave a 4028 bytes: con el payload de 4066 bytes, una entrada interna requiere 28 bytes fijos más 10 bytes y la clave como separador. `ProjectStore` aplica el mismo límite a la clave compuesta versionada.

`occupancy_diagnostics()` informa hojas no raíz vacías, internos no raíz unarios y raíces internas unarias. También cuenta hojas e internos no raíz y mide bytes lógicos de cabecera y entradas, excluyendo el relleno físico que completa cada página; acumula tamaños mínimo/máximo por tipo y ofrece totales agregados (`non_root_pages`, `non_root_payload_bytes`, `underfilled_non_root_pages`) junto con el desglose por tipo. Clasifica como subocupadas las páginas cuyo contenido lógico ocupa menos de un tercio de los 4066 bytes útiles y devuelve el umbral exacto en `minimum_diagnostic_occupancy_bytes`; es una señal de mantenimiento, no una invariante para claves/valores de longitud variable. Detecta ciclos y referencias compartidas, pero no altera ni rechaza árboles alcanzables: hace observable la deuda de compactación mientras se completa la reparación descendente.

La implementación sigue siendo experimental. `insert()` y `remove()` públicos crean una `MutationSession` y confirman el overlay mediante una única transacción MLPJ. La eliminación staged captura el camino y repara déficits locales. `repair_occupancy()` añade un recorrido explícito de todo el árbol: recoge hojas vacías, nodos internos unarios y páginas no raíz subocupadas por bytes; re-resuelve padres sobre el overlay, repite las reparaciones hasta converger y publica el resultado en una única transacción WAL. Si la preparación falla o no converge, no publica imágenes parciales. Integra redistribución por bytes entre hojas hermanas bajo el mismo padre y fusión de páginas cuando la carga combinada cabe en una sola; combina sus entradas ordenadas, calcula el corte, actualiza el separador padre y stagea las tres imágenes en un único overlay antes del commit WAL. La misma reparación integra redistribución y fusión de nodos internos hermanos cuando la carga combinada cabe en una sola página: incorpora el separador padre al conjunto ordenado, promueve el nuevo separador, redistribuye los punteros hijos y verifica la capacidad del padre antes de stagedar las tres páginas. Ambas rutas mantienen la atomicidad del overlay/WAL. No tiene buffer pool ni compactación física de páginas. Las pruebas siguen sin ejecución confirmada. No debe usarse aún como almacenamiento de manuscritos.

### Diario de imágenes MLPJ v2

Coordina WAL de imágenes completas con MLPG. Una transacción contiene BEGIN, una o más IMAGE y COMMIT. Valida todos los cambios antes de escribir; asigna IDs contiguos a páginas nuevas y rechaza páginas duplicadas en una misma transacción. Sincroniza el WAL antes de aplicar las imágenes y repite redo al abrir. Puede continuar una aplicación parcial y reparar páginas dañadas desde imágenes confirmadas.

`DurablePages::open()` rechaza rutas equivalentes para el archivo de páginas y el WAL, evitando abrir el mismo archivo en dos formatos incompatibles. `DurablePages::checkpoint()` sincroniza primero todas las páginas y luego trunca MLPJ a su cabecera de 12 bytes. Esto compacta el diario de imágenes, no el archivo de páginas ni el WAL de registros. El orden permite recuperar sin el WAL antiguo porque las páginas ya se han sincronizado. MLPJ v1 no es compatible con el lector v2 y no existe migrador automático.

### Eliminación dentro de MutationSession

`remove()` ya delega en `remove_in_session()` y comparte el overlay con inserciones staged. Las eliminaciones pueden observar splits y raíces creados anteriormente en la misma sesión; la metadata de raíz se stagea para que los lectores de ancestros resuelvan correctamente esa estructura antes del commit. La reparación local durante `remove()` sigue el camino afectado. Para mantenimiento explícito, `repair_occupancy()` recorre el árbol completo y repara hojas vacías y nodos internos unarios en una sesión transaccional única. `ProjectStore::apply_batch` ya expone la primera API pública batch; sus pruebas de semántica secuencial, aislamiento, rechazo previo al staging y reapertura están escritas, pero todavía no tienen ejecución confirmada.

### Generaciones publicadas y copias de trabajo

`publication.rs` expone `PublishedProjectStore` como fachada de solo lectura para la generación activa. La apertura de miembros publicados utiliza descriptores OS read-only, no inicializa ni recupera el WAL, exige que contenga únicamente su cabecera checkpointed y bloquea transacciones/checkpoints también en `DurablePages`; la fachada no depende solo de ocultar métodos de escritura. `PublicationStore::create_working_copy([u8; 16])` clona en streaming todos los espacios `project_id` de la generación a un ProjectStore independiente bajo `working/`, preservando las claves compuestas y el aislamiento entre proyectos, con directorio privado, WAL propio y manifiesto `WORKING.MANIFEST` que registra el ID opaco aportado por el anfitrión y la generación base. La copia solo aparece con su nombre definitivo después de copiar, validar, checkpointar y cerrar el almacén temporal. `open_working_copy(id)` permite reanudarla después de cerrar/reiniciar el proceso usando `ProjectStore::open_existing` (no recrea archivos ausentes), y `open_or_create_working_copy(id)` crea o reanuda sin aceptar temporales incompletos; `WorkingProjectStore` expone las mutaciones y consultas sobre esa copia, no sobre la generación publicada.

`publish_working_copy(working, publication_id)` conserva el flujo anterior de un único almacén. Para el par vivo/narrativo se usa `WorkingBundle`: copia ambos miembros de una misma generación, mantiene un lock de sesión, permite reanudación y rechaza archivos faltantes. `publish_working_bundle(working, publication_id)` consume la sesión, abre ambos miembros con verificación de descriptores y el mismo validador de sesión, checkpointa y valida los dos miembros, verifica que todos los registros pertenezcan al `project_id` del anfitrión, prepara ambos receipts y un manifiesto común, y revalida el lock en cada frontera de preparación y antes/durante la conmutación del selector raíz, que ocurre una sola vez. Las working bundles obsoletas se rechazan; no existe rebase/merge automático. Los temporales y copias de trabajo no se eliminan automáticamente; la política de retención sigue pendiente. `HostEngineApi::open_working_bundle` conserva el lock mientras el worker y el almacén narrativo están abiertos; `into_working_bundle` cierra ambos y devuelve la sesión para su publicación conjunta. Hay pruebas escritas para clonación, reapertura, publicación conjunta, corrupción, archivos faltantes, aislamiento por proyecto e integración con el worker. Las pruebas de sesión sustituyen el lock entre ambos checkpoints, durante la preparación de la generación y después de sincronizar el selector temporal; verifican que no se publique una generación parcial, que el miembro narrativo no se checkpointée tras perder la sesión y que el selector anterior permanezca activo antes del hardlink. Aún no hay ejecución confirmada.

## Pruebas escritas

Hay **445 pruebas unitarias escritas en almacenamiento**, verificadas contando los atributos `#[test]` de los módulos fuente:
- 14 del WAL de registros legado, incluidas pruebas de escritura parcial, error ambiguo después de un COMMIT durable, corrupción interior, checksum inválido y secuencias de IDs no consecutivas; la recuperación falla cerrada ante frames completos inválidos.
- 3 del visitante de snapshot `Store::visit_records`: orden determinista, preservación de bytes binarios/Unicode/NUL, propagación de errores y rechazo de instancias ambiguas.
- 7 de importación MLWAL→ProjectStore: importación real por lotes, verificación de cada clave/valor y reapertura de ambos almacenes; división por presupuesto de bytes antes de alcanzar el máximo de operaciones; rechazo de tamaños de lote inválidos/destinos no vacíos; importación de origen vacío sin COMMIT vacío; fallo tras un lote confirmado que demuestra que el destino parcial no debe publicarse; rechazo de un registro individual que supera el límite de 128 KiB por copia antes de staging (se reservan dos copias lógicas para escritura/verificación, sin contar overhead de allocator); y verificación byte por byte de que el WAL legado permanece intacto tras una importación completa.
- 8 del archivo MLPG.
- 3 de páginas slotted.
- 9 del codec de nodos B+Tree, incluidas pruebas de capacidad exacta de nodo interno (64 bytes) y rechazo al excederla por un byte.
- 155 del B+Tree persistente: diagnóstico de ocupación lógica por bytes para hojas e internos no raíz con umbral explícito de un tercio y pruebas independientes de clasificación para ambos tipos de nodo; planificadores de redistribución de hojas e internos con elección por bytes, preferencia por eliminar subocupación, límites de capacidad y rechazo de cortes inválidos o que crearían nodos internos unarios; reparación global que ya integra redistribución transaccional por bytes entre hojas hermanas desde ambos lados, actualización del separador padre y recuperación WAL tras aplicación parcial;  apertura/reapertura, búsqueda, reemplazo, splits, raíces multinivel, rangos e iteradores (incluida detección de ciclos entre hojas y rechazo de enlaces fuera del archivo), redistribución/fusión, reparación descendente con redistribución interna desde ambos lados y fusión hacia la izquierda para el hijo central de un padre con tres hijos, fusión del primer hijo hacia su hermano derecho con contracción de raíz, cadena MBFR y reutilización de la primera página liberada tras reabrir sin crecimiento del archivo de varias fusiones internas en una sola pasada y cascada multinivel con contracción de raíz, cadena MBFR, recuperación tras apply parcial, reaperturas y reutilización de la antigua página raíz; mantenimiento global de ocupación sobre una cadena persistida de tres raíces unarias con verificación de MBFR y no-op tras reabrir; recuperación WAL del mantenimiento global después de una aplicación parcial de imágenes; también se inyectan candidatos repetidos y páginas liberadas durante la misma pasada para verificar que no se procesen dos veces, además de la actualización de los separadores del padre, liberación/reutilización, contracción, validación y secuencias mixtas contrastadas con `BTreeMap`, y reutilización MBFR dentro de una misma sesión y borrado total en orden pseudoaleatorio con una sola sesión, abandono seguro de una sesión tras una eliminación staged, además de verificar que un `remove()` público de clave ausente no cambie tamaños de páginas/WAL, generaciones, raíz ni contenido incluso tras reabrir, tanto en un árbol pequeño como en uno multinivel de 450 registros con métricas de ocupación intactas, y 720 mutaciones públicas generadas con cuatro semillas, comparación operación por operación con `BTreeMap` y reaperturas periódicas. Además, 336 eliminaciones públicas en tres órdenes pseudoaleatorios, validación contra `BTreeMap` después de cada borrado, comprobación del inventario de páginas y de los tamaños mínimo/máximo de payload contra `validate()` en cada estado intermedio y después de cada reapertura, y comprobación final de árbol vacío y ausencia de déficits no raíz. Una prueba adicional repite ese `remove()` público con fallos inyectados después de 0 a 8 imágenes aplicadas; en cada caso exige cuarentena de la instancia y, tras dos reaperturas, comprueba el estado posterior completo, la clave eliminada ausente, la superviviente intacta y ambas páginas retiradas en MBFR. También se comprueba la aceptación de una entrada que ocupa exactamente el payload de hoja (4066 bytes), el split posterior y el rechazo atómico de un valor un byte mayor, incluso tras reabrir. Se añade una sesión de 450 inserciones staged que fuerza la división de la raíz interna, exige altura mínima 2 y verifica el árbol completo tras reabrir. También se prueba el límite de clave de 4028 bytes: puede convertirse en separador interno de exactamente 4066 bytes tras dividir una hoja; una clave de 4029 bytes se rechaza antes de modificar páginas y sigue ausente tras reabrir. Se prueba además la división de una raíz interna que contiene dos separadores de tamaño máximo, tanto en la primitiva de split como con tres claves máximas insertadas en el árbol, validado y reabierto. Se verifica también que `split_internal()` elija el separador que equilibra el tamaño codificado cuando las longitudes son muy distintas, y que las fusiones internas izquierda/derecha con un separador máximo ocupen exactamente el payload permitido. `ProjectStore` comparte ese mismo límite al validar las identidades compuestas, antes de codificarlas o tocar el árbol. El B+Tree preflighta el número final de imágenes antes de iniciar la transacción MLPJ y prueba el límite exacto y el rechazo de una imagen adicional. Se añadió una prueba con cinco claves máximas que fuerza divisiones internas sucesivas hasta una raíz de nivel 3 (cuatro niveles contando las hojas), valida todas las búsquedas y comprueba la reapertura. ### Selector durable de publicación

Se añadió `src/publication.rs`, exportado como `publication`. `PublicationPointer` codifica generación, `migration_id`, directorio de generación determinista y checksum SHA-256. Cada generación incluye `GENERATION.MANIFEST`, con tamaños y hashes SHA-256 de `store.pages` y `store.mlpj`, además del checksum del receipt. `PublicationStore` usa dos slots alternos `CURRENT.0`/`CURRENT.1`, conserva el slot activo al escribir el inactivo, sincroniza el selector y rechaza slots corruptos, saltos de generación, enlaces simbólicos y rutas que no correspondan a la identidad. `resolve_paths()` valida receipt, identidad y tamaños; `resolve_current_paths()` verifica además los hashes completos antes de devolver las rutas. **Estas funciones devuelven rutas, no descriptores verificados**: existe una ventana entre el hash y la apertura posterior que debe cerrarse antes de usar generaciones publicadas con datos reales. La apertura integrada usa descriptores del sistema operativo sin permiso de escritura y verifica SHA-256 sobre esos mismos descriptores; exige MLPJ checkpointed y no ejecuta recovery, redo, truncado ni sync sobre una generación publicada. Como el publicador hace checkpoint antes de copiar, tanto la publicación como la apertura exigen que MLPJ conserve solo su cabecera de 12 bytes; una generación con WAL pendiente no puede publicarse ni abrirse como inmutable, evitando modificarla durante recovery. La API pública devuelve `PublishedProjectStore`, una fachada de solo lectura que ofrece consultas y recorridos paginados sin exponer put/delete/checkpoint. Esta fachada también se utiliza como miembro read-only de `PublishedBundle`; la escritura coordinada requiere `WorkingBundle` y `publish_working_bundle`, nunca mutar la generación publicada. Tras un error ambiguo de publicación, exige cerrar y reabrir. La orquestación de copia, verificación, publicación y transición del manifiesto está implementada en `migration::publish_verified_legacy_snapshot()` y su recuperación en `migration::reconcile_legacy_snapshot_publication()`; la integración con el backend anfitrión sigue pendiente.

### Publicación verificada de generaciones

La API `migration::publish_verified_legacy_snapshot` exige estado `Verified`, identidad/rutas coincidentes y vuelve a comprobar que el WAL de origen sigue teniendo el fingerprint y contadores del manifiesto. Ejecuta checkpoint del destino temporal, copia ambos archivos en streaming con SHA-256 y `sync_all`, escribe un receipt durable con hashes/tamaños, reabre la pareja copiada, valida el B+Tree y compara cada identidad/valor contra el origen. La publicación verifica de nuevo los hashes completos antes de cambiar el selector. Solo entonces publica el selector. Los archivos temporales originales no se mueven ni se sustituyen.

Si el proceso cae después de publicar el selector y antes de persistir `Published`, `migration::reconcile_legacy_snapshot_publication` reabre la generación activa, la compara de nuevo contra el origen y completa la transición. Si la fuente cambió, los bytes difieren o el manifiesto no corresponde, no se publica ni se marca como Published. La reconciliación mantiene un guard de snapshot del origen durante toda la comparación y transición, bloqueando escrituras concurrentes del mismo Store. La limpieza de una generación huérfana de reintento toma los bloqueos de sus archivos y conserva los lockfiles persistentes. La reconciliación no hace rollback automático del selector.

### Importación reanudable MLWAL → ProjectStore

`import_legacy_snapshot_resumable()` incorpora checkpoints durables por lote mediante `ManifestStore`. Antes de importar calcula un fingerprint determinista del snapshot y sus contadores; luego importa en lotes MLPJ, verifica cada registro y persiste cursor, secuencia, contadores y hash del prefijo después de cada COMMIT. Al reabrir, vuelve a recorrer el origen, verifica el prefijo ya importado contra el destino y continúa después del cursor. Si encuentra registros de destino adicionales respecto del checkpoint, verifica que sean exactamente el lote que pudo confirmarse antes de una caída y adopta ese progreso sin duplicar escrituras. Rechaza discrepancias, cambios del origen, cursores incoherentes y destinos con registros inesperados. La importación finaliza en `ImportComplete`. La verificación independiente se ejecuta por separado mediante `verify_legacy_snapshot_migration()`: pasa el manifiesto a `Verifying`, valida la estructura del destino, recorre origen y destino en orden global de clave, compara cada identidad y valor byte por byte, detecta registros faltantes/adicionales, vuelve a calcular recuento, bytes y fingerprint, y solo entonces persiste `Verified`. El recorrido completo del destino usa `ProjectStore::scan_all_iter()`, que no materializa el almacén entero. Si encuentra una divergencia, deja el manifiesto en `Verifying`; después de corregir el destino, la verificación puede repetirse. Esta fase no publica ni reemplaza archivos.

El fingerprint del origen y del prefijo usa SHA-256 incremental, probado con vectores estándar de bloque simple y múltiple. El checksum FNV-1a del contenedor del manifiesto sigue siendo un control de corrupción, no una firma criptográfica. La ruta de importación reanudable mantiene el destino sin publicar ante errores. Se añadieron trece pruebas escritas para esta ruta: importación por lotes y reapertura, snapshot vacío, rechazo de destino discordante, recuperación del COMMIT sin checkpoint, aborto por origen modificado, rechazo de registros demasiado grandes, verificación exacta exitosa, rechazo de valores alterados, registros faltantes y adicionales, y reintento de verificación tras corregir el destino.

### Bloqueo entre procesos

Se implementó un guard no clonable con archivo auxiliar persistente `.mldb-lock`: `flock(LOCK_EX | LOCK_NB)` en Unix y `LockFileEx` no bloqueante en Windows. `Store::open` bloquea el WAL antes de abrirlo; `DurablePages::open` adquiere en orden estable los bloqueos de MLPG y MLPJ antes de recovery. Si falla una adquisición múltiple, los guards ya obtenidos se liberan al salir del ámbito. El error `AlreadyLocked` identifica una apertura concurrente.

Las pruebas cubren exclusión entre aperturas del mismo proceso y entre procesos hijos, liberación normal y tras terminación abrupta del proceso propietario, liberación de bloqueos parciales, creación de directorios padre inexistentes, normalización de rutas equivalentes con `..` y rechazo de enlaces simbólicos en Unix. La canonicalización del directorio padre ocurre después de asegurar su creación, evitando que la apertura falle prematuramente en rutas nuevas. El guard también permite revalidar su identidad durante la sesión, y DurablePages realiza esa comprobación antes de transacciones y checkpoints para detectar la sustitución del archivo auxiliar. Dos pruebas adicionales sustituyen la ruta MLPG o MLPJ durante una sesión y exigen que la transacción falle antes de añadir frames, preservando el WAL y las páginas originales. Otras dos sustituyen esas rutas antes de un checkpoint y comprueban que el diario no se trunque ni se alteren las páginas originales. Una prueba adicional sustituye el lock de sesión de una working bundle y verifica que el bloqueo independiente de páginas/WAL impida abrir un segundo escritor mientras el primero conserva la sesión. La suite del motor también incluye una prueba de integración que sustituye el lock durante una sesión activa y comprueba que el worker rechace el siguiente delta durable y la API rechace una escritura de conocimiento. **No se han ejecutado las pruebas**, y aún faltan escenarios de terminación forzada y CI nativo. Los backends Windows/Unix tampoco han sido compilados aquí; Android/iOS no se declaran soportados hasta validación nativa. Consultar [INTERPROCESS_LOCKING.md](INTERPROCESS_LOCKING.md) para el contrato y límites.

### Codecs de reutilización (etapa experimental)

`src/page_reuse.rs` incorpora codecs aislados para MBTR v2 y MBFR v1. MBTR v2 se emite con `TreeMetadata::encode`; `decode` acepta MBTR v1 (24 bytes) como lista libre vacía y v2 (32 bytes) con `free_head`. `FreePage` codifica/decodifica el marcador MBFR v1 de 16 bytes. Hay ocho pruebas unitarias escritas para compatibilidad, roundtrip, sentinelas y rechazo de datos corruptos. Estos codecs ya están integrados parcialmente con `PersistentBPlusTree`: el árbol escribe MBTR v2, lee MBTR v1/v2, valida la lista MBFR, consume páginas libres al insertar y libera hojas durante fusiones locales.


### Integración de metadata MBTR v2

`PersistentBPlusTree` ahora escribe metadata MBTR v2 y puede abrir metadata MBTR v1 existente, interpretando su lista libre como vacía. La actualización de raíz conserva `free_head`. Se añadió una prueba de integración de codec para escritura v2 y lectura v1. La integración posterior añadió consumo de páginas MBFR durante inserciones y liberación de hojas vacías en fusiones locales, con actualización transaccional de la metadata. 


`PersistentBPlusTree::validate()` también recorre `free_head`, comprueba cada MBFR, detecta ciclos y duplicados, impide solapamiento entre páginas alcanzables y libres, y exige que todas las páginas físicas pertenezcan exactamente a uno de esos conjuntos. `ValidationReport` informa `free_pages`. La inserción y las divisiones de hojas/nodos ya consumen páginas de `free_head` cuando están disponibles; el cambio de lista y la escritura del nodo se confirman en una misma transacción MLPJ. `remove()` ahora puede fusionar hojas vacías cuando el hermano no puede donar, convertir la página retirada en MBFR y contraer una raíz interna que queda con un solo hijo. La liberación de nodos internos no raíz y la propagación ascendente están integradas; `remove()` añade una pasada descendente acotada para nodos internos unarios y hojas vacías del camino afectado. La ocupación mínima global y la compactación siguen pendientes.


La ruta de inserción reserva páginas desde `free_head` antes de ampliar el archivo. Al reutilizar una página, valida su MBFR, avanza la cabeza de lista y sobrescribe esa página con una generación incrementada dentro de la misma transacción que escribe el nuevo nodo y actualiza la metadata MBTR. Las divisiones de hojas conocen el ID reservado antes de codificar `next_leaf`. Si la transacción no se confirma, WAL no aplica ni la retirada ni el nuevo nodo.


### Fusión y liberación de hojas (etapa experimental)

Cuando una eliminación deja una hoja vacía, `remove_in_session()` intenta redistribuir desde un hermano con más de una entrada o fusionar con el hermano adyacente, actualiza `next_leaf` y el separador del padre, y libera la página retirada como MBFR. Si la raíz queda unaria, la contrae al hijo superviviente. La reparación descendente revisa los nodos internos unarios capturados en el camino y puede redistribuirlos o fusionarlos con hermanos del mismo nivel; las páginas liberadas, `free_head`, raíz y metadata permanecen en el mismo overlay y se confirman en una única transacción MLPJ. Hay pruebas de ambos lados de redistribución, fusiones internas, contracción multinivel y reapertura. La cobertura sigue siendo parcial y no garantiza ocupación mínima global.



**Límite conocido de `remove()`:** la reparación se limita a la hoja afectada y a los nodos internos del camino original; vuelve a resolver cada padre contra el overlay vigente después de las fusiones. Si no existe un hermano válido o una fusión no cabe en una página, puede persistir un déficit de ocupación o la operación puede devolver un error de planificación antes del commit. No se ejecuta compactación global ni se garantiza ocupación mínima global.


### Primitivas y rebalanceo interno integrado — etapa parcial

`src/btree.rs` ahora contiene funciones puras para rotar un hijo/separador desde el hermano interno izquierdo o derecho y para fusionar dos nodos internos incorporando el separador del padre. Nueve pruebas unitarias comprueban el movimiento exacto de hijos y separadores en ambas direcciones, la inclusión del separador padre en fusiones y la ida y vuelta por el codec MBTN de los nodos resultantes. Estas primitivas ahora se utilizan desde `remove_in_session()` para redistribución/fusión de nodos internos unarios cuando encuentran un hermano del mismo nivel. La integración incluye una pasada descendente acotada que vuelve a resolver los padres sobre el overlay; cubre donación desde ambos lados, fusión con separador del padre y contracción de raíces staged. Todavía no cubre todos los patrones multinivel ni garantiza ocupación mínima global. Las pruebas están escritas, pendientes de resultado CI.


El staging de sobrescrituras coalesce las imágenes de cada página conservando la generación original. `PageOverlay` representa sobrescrituras, páginas liberadas, páginas MBFR registradas y asignaciones nuevas; `remove()` opera ahora directamente con el overlay compartido de `MutationSession`; las eliminaciones sin reparación pendiente también pasan por el overlay validado antes de confirmar una sola transacción MLPJ. Antes del commit, `PageOverlay::validate()` comprueba continuidad de IDs asignados, generación inicial, límites de payload, consistencia de estados MBFR, enlaces libres que no apunten a páginas staged vivas ni formen ciclos entre estados staged, y `root_id`/`free_head` dentro del rango lógico sin solapamiento. `allocate_node()` ya construye el overlay a partir de los cambios recursivos de inserción y consume `free_head` mediante `stage_consume_free_head()`. La inserción utiliza así el mismo mapa de estado para coalescer imágenes, reutilizar páginas MBFR persistidas o liberadas en la misma transacción y emitir una sola imagen final por ID. Antes del WAL commit, `insert()` vuelve a importar el conjunto completo —incluida la metadata MBTR final— y valida raíz, `free_head`, asignaciones y estados de página en una sola vista. La prueba `insert_reuses_free_page_for_leaf_split_atomically` cubre la ruta integrada; las pruebas del overlay cubren generaciones y transiciones. El overlay ahora usa un único `BTreeMap<page_id, OverlayPageState>` con estados mutuamente excluyentes (`LiveExisting`, `FreedExisting`, `ReusableExisting`, `LiveAllocated`, `FreedAllocated`); las transiciones inválidas se rechazan al stagear y el validador comprueba la coherencia antes de persistir. 

La acumulación de sobrescrituras admite también la página 0 de metadata: el identificador cero es válido y no debe confundirse con una página ausente. 

La recuperación de páginas también tiene cobertura multipágina: reconstrucción de la última página truncada durante una asignación y durante una transacción de sobrescrituras, con verificación después de una segunda reapertura. Si el WAL confirmado está corrupto, la apertura falla sin modificar ni truncar la cola física parcial ni el diario, preservando ambos para diagnóstico.


El diagnóstico de ocupación también clasifica hojas e internos no raíz cuyo payload codificado es inferior a un tercio de la capacidad útil de 4066 bytes. Es una métrica de mantenimiento y no una condición de validez ni una reparación automática por umbral.


### Recuperación e integridad del bundle — cobertura añadida

La matriz de interrupciones del selector ahora comprueba la reapertura tras fallar inmediatamente después de sincronizar el temporal, después de crear el hard link y después de sincronizar la raíz. Los fixtures usan contenidos distintos en cada generación y verifican por separado el miembro vivo y el narrativo: la reapertura no puede combinar revisiones. Los temporales de selector que sobreviven se inventarían, pero no se adoptan ni eliminan.

También hay pruebas que dañan individualmente el manifiesto común, ambos receipts, las páginas y los WAL de ambos miembros de la generación más reciente. Aunque el slot anterior siga siendo válido, BundlePublicationStore::open() debe fallar cerrado; no retrocede silenciosamente a una generación antigua. La verificación de descriptores publicados en Windows compara volumen e índice de archivo, exige un único enlace y comprueba metadatos estables, con una regresión específica para hardlinks.

Estas pruebas están escritas, pero no ejecutadas en este entorno: GitHub no informa workflows para los commits recientes y aquí no se ha ejecutado cargo test/cargo check. Las interrupciones se simulan en límites del protocolo mediante hooks y reapertura del almacén; no equivalen a cortar la alimentación ni prueban pérdida de cachés del dispositivo. En Unix se sincronizan los directorios con sync_all; en Windows el helper actual no realiza un flush de directorio porque la biblioteca estándar no ofrece una operación portable equivalente. Por tanto, no se debe afirmar todavía una garantía de durabilidad ante pérdida súbita de energía en Windows.


## Integración continua nativa

El repositorio incluye `.github/workflows/motor-literario-rust.yml`, que ejecuta `cargo test --workspace --all-targets --locked` en `ubuntu-latest` y `windows-latest` ante cambios del Motor Literario, pull requests y ejecución manual. La existencia del workflow no implica que una ejecución haya terminado: consultar el resultado de cada commit antes de declarar validada la compilación o la suite.
